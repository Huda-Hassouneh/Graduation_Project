# Milestone 3: Gazebo models, facade worlds and kinematic replay

Verified 2026-10-30 with Gazebo Sim 8.15.0 (Harmonic), SDFormat 14, gz-transport 13 /
gz-msgs 10 Python bindings (`/usr/lib/python3/dist-packages`), on Ubuntu 24.04 under WSL 2.

> **Update (2026-11-01):** the DJI Matrice 400 phase added the static replay model `dji_matrice_400`,
> the Gazebo-physics flight model `dji_matrice_400_flight` and the worlds `facade_complex_m400` and
> `m400_flight_test`; `check_worlds.py` now checks all four worlds. See docs/SIMULATION_MODEL.md §9.

## Role of Gazebo

Gazebo is used **only for visualisation and scenario geometry**. The Python simulator is still
the only dynamics and controller implementation. In both worlds the aircraft is a **static**
model. A replay applies the logged truth pose (`p_*`, `q_*`) to that model through
`/world/<world>/set_pose_vector`. Gazebo integrates no vehicle dynamics, so a replay shows what
the Python simulator computed. It is not evidence that the dynamics are correct. Keep-out
boxes are visual markers only: they have no collision and nothing enforces them.

## Files

| Path | Content | Generated by |
|---|---|---|
| `simulation/models/<aircraft>/model.sdf`, `model.config` | aircraft models | `simulation/models/generate_models.py` |
| `config/visual/<aircraft>.yaml` | appearance and contact shapes only (all `source: assumed` except the M400 published envelope) | hand-written |
| `simulation/worlds/facade_{flat,complex}.sdf` | facade worlds | `simulation/worlds/generate_facade_world.py` |
| `simulation/worlds/facade_*.geometry.json` | every solid and keep-out box in world coordinates (for tests and later planners) | same |
| `simulation/gazebo/env.sh` | sets the model search paths in the current shell | hand-written |
| `simulation/gazebo/launch_world.sh` | launches a world with the paths set | hand-written |
| `simulation/gazebo/check_worlds.py` | SDF check, headless load, optional replay check | hand-written |
| `simulation/gazebo/replay_run.py` | kinematic replay of `results/runs/<id>` | hand-written |

The generated files are deterministic. Tests fail if the committed files differ from what the
generators produce. After changing an aircraft or visual YAML, run the generator.

## Aircraft models

* A single link `base_link`, with its origin at the CoM and FLU axes. Mass and the full inertia
  tensor come from `config/aircraft/<aircraft>.yaml` (same derivation as the Python simulator).
* Rotors are SDF `<frame>`s `rotor_1..4` at the configured hub positions. The spin direction
  is shown in the visual name (`rotor_<i>_ccw_disk` / `_cw_disk`) and in its colour. The disk
  diameter equals `rotor_diameter`. This **deviates from the M3 plan** in next_steps.md
  ("rotor joints"). Nothing in Gazebo actuates the rotors, and a separate rotor link would need
  propeller inertia that the configuration does not provide.
* `m400_reference_quad` is an **M400-inspired quadrotor, not a DJI Matrice 400 digital twin**
  (stated in the SDF header and `model.config`). Only the 980 × 760 × 480 mm translucent
  envelope box uses manufacturer data. The airframe extent is 908 × 837 × 480 mm. Its width
  exceeds the published 760 mm because a square X with the configured 1070 mm diagonal places
  the hubs 757 mm apart, so the motor housings stick out. This is a consequence of the
  quadrotor assumption (docs/aircraft_reference.md), not a modelling error in the SDF.

## Facade worlds

Frame: ENU world, origin = take-off point (2 m pad at the origin). The main building face is
exactly the scenario facade from `experiments/scenarios.py`: the plane y = 8 m, x ∈ [0, 12] m,
outward normal −y, height 12 m. The constants `FACADE_WIDTH_M`, `SCAN_Z_MIN_M` and
`SCAN_Z_MAX_M` were moved into named constants in `scenarios.py` so that the world generator
and the tests read the same values as the scenarios. Their values (12, 3, 9 m) are unchanged,
so the baseline results are unaffected.

* `facade_flat`: one 12 × 10 × 12 m block.
* `facade_complex`: the same main block plus a neighbour block recessed by 2 m
  (x ∈ [−6, 0]), a wing protruding 1.5 m (x ∈ [12, 16], face at y = 6.5 m) and four
  balconies (1.2 m deep, at 4 m and 7 m) with railings.
* Keep-out boxes: each solid is inflated by 1 m toward the flight side (balconies include the
  railing).

All dimensions beyond the scenario face are assumptions (`FacadeWorldSpec`).

## Model path (why manual launches failed)

The worlds include the aircraft as `model://research_quad`. Gazebo resolves this only through
search paths:

| Tool | Variable |
|---|---|
| `gz sim` (server) | `GZ_SIM_RESOURCE_PATH` |
| `gz sdf -k` / `-p` | `SDF_PATH` |

In a fresh shell both are empty. `gz sim` then exits with `Unable to find
uri[model://research_quad]` and `gz sdf -k` reports the same error. The tests always set the
paths themselves (`graduation_project.gazebo.gazebo_env()`), so they passed while manual
commands failed. `simulation/gazebo/env.sh` prepends `<repo>/simulation/models` to both
variables. The path is derived from the script's own location, so it works with any checkout
path, including one with spaces. The scripts below set it themselves.

## Commands (from a clean WSL terminal, repository root)

```bash
# Validate both models and worlds: gz sdf -k + headless load of each world (~15 s)
python3 simulation/gazebo/check_worlds.py
# ... and additionally replay a run into each world and check the final pose
python3 simulation/gazebo/check_worlds.py --replay results/runs/<experiment_id>

# Launch a world with the GUI
simulation/gazebo/launch_world.sh facade_flat
simulation/gazebo/launch_world.sh facade_complex

# Launch headless (server only, simulation running)
simulation/gazebo/launch_world.sh facade_flat --headless
simulation/gazebo/launch_world.sh facade_complex --headless

# Replay a Python-simulator run into the running world (second terminal; no setup needed)
python3 simulation/gazebo/replay_run.py --world facade_flat --run results/runs/<experiment_id> [--speed 2]

# Alternative: configure the shell once, then use gz directly
source simulation/gazebo/env.sh
gz sdf -k simulation/worlds/facade_complex.sdf
gz sim simulation/worlds/facade_complex.sdf
```

`--world` for `replay_run.py` must match the running world. If the run's aircraft is not in
the world (for example `m400_reference_quad` in these worlds), it is spawned as a static model.
A green sphere marks the reference position. `env.sh` is written for bash, the WSL default.
To make it permanent, add `source "<repo>/simulation/gazebo/env.sh"` to `~/.bashrc`.
The GUI was not exercised during verification; only headless runs were.

| `check_worlds.py --replay` facade_parallel / research_quad, both worlds | 1696 frames; final Gazebo pose equals last logged pose |
| `launch_world.sh facade_complex --headless` + `replay_run.py` helix_3d / m400_reference_quad | M400 spawned; final pose [0.3368, 2.9988, 4.1142] m, roll 0.0767 rad, matches the log |
| `pytest` (all, including `slow`) | 143 passed |
| Flown baseline facade runs vs world geometry (both aircraft, both worlds) | no logged CoM sample inside a solid or a keep-out box |

Closest approach: in `facade_complex` the 3 m stand-off plane (y = 5 m) passes the wing face
(y = 6.5 m) at x = 12 m. CoM-to-wall distance is 1.5 m, or 0.65 m after subtracting the
M400 reference half-span (hub radius + rotor radius, 0.85 m). The research_quad has 1.15 m.
The CoM passes 0.5 m outside the wing keep-out box. Tests check reference points against the
keep-out boxes; they do not account for the vehicle footprint.
